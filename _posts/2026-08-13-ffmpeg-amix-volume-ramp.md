## 문제

문장별로 합성한 나레이션 21개를 `adelay`로 시각에 배치하고 `amix`로 한 트랙에 합쳤다. 들어보니 **앞부분은 잘 안 들리는데 뒷부분은 귀가 아팠다.**

느낌이 아니라 값으로 확인하려고 8초 구간씩 잘라서 재봤다.

```bash
for a in 0 8 16 24 32 40; do
  ffmpeg -hide_banner -ss $a -t 8 -i out.mp4 -map 0:a -af volumedetect -f null - 2>&1 \
    | grep -E "mean_volume|max_volume"
done
```

```
 0~ 8초   평균 -43.4 dB   최대 -26.7 dB
 8~16초   평균 -42.4 dB   최대 -25.7 dB
16~24초   평균 -39.1 dB   최대 -23.2 dB
24~32초   평균 -36.1 dB   최대 -20.2 dB
32~40초   평균 -29.9 dB   최대 -13.1 dB
40~48초   평균 -21.1 dB   최대  -1.5 dB
```

**단조롭게 계속 커진다.** 앞뒤로 평균 22dB, 최대 25dB 차이다. 소재는 전부 같은 엔진으로 같은 설정에서 합성한 음성이라 원본 크기 차이는 아니다.

## 원인

`amix` 필터의 `normalize` 옵션이 범인이다. **기본값이 `1`(켜짐)이고, 이건 "지금 살아 있는 입력 수"로 나눈다.**

내가 만든 필터그래프는 이렇게 생겼다.

```
[0:a]adelay=1800|1800[a0];
[1:a]adelay=3800|3800[a1];
…
[20:a]adelay=44200|44200[a20];
[a0][a1]…[a20]amix=inputs=21:duration=longest:dropout_transition=0[mix]
```

각 입력은 **"무음 → 문장 → 끝"** 구조다. `adelay`가 앞에 무음을 붙이고, 문장이 끝나면 그 스트림은 EOF에 도달한다.

- **영상 시작 시점**: 21개 입력이 전부 살아 있다 → 각 입력이 **1/21**로 줄어든다
- **중반**: 앞쪽 문장들이 하나씩 끝난다 → 나누는 수가 줄어 점점 커진다
- **마지막 문장**: 살아 있는 입력이 1개 → **원래 크기 그대로** 나온다

그래서 **정확히 문장이 끝나는 개수만큼 계단식으로 커진다.** 위 실측 곡선이 우상향하는 이유가 이것이다.

> `dropout_transition`을 0으로 둬도 소용없다. 그건 **전환을 부드럽게 하는 시간**일 뿐, 나누기 자체를 끄지 않는다.
{: .prompt-warning }

## 해결 과정

### normalize=0

나누기를 끈다.

```
amix=inputs=21:duration=longest:dropout_transition=0:normalize=0
```

이러면 각 입력이 원래 크기 그대로 더해진다. 내 경우엔 문장들이 시간상 겹치지 않으므로 합산으로 인한 클리핑 걱정도 없다.

> 입력이 **동시에 울리는** 상황이라면 얘기가 다르다. `normalize=0`으로 그냥 더하면 클리핑이 난다. 그때는 각 입력에 `volume`으로 미리 여유를 주거나, 아래 2패스 보정으로 마지막에 맞춰야 한다. 단 2패스로 맞추려면 1패스를 **32비트 float**로 뽑아야 한다. 이유는 아래 [겹치는 소리와 2패스의 함정](#겹치는-소리와-2패스의-함정)에 실측과 함께 정리했다.
{: .prompt-tip }

### 2패스로 최고점 맞추기

`normalize=0`만 하면 이번엔 전체 크기가 소재에 좌우된다. 그래서 **한 번 뽑아서 최고점을 재고, 목표치와의 차이만큼 보정**했다.

```bash
# 1패스 — 보정 없이 합치기만
ffmpeg -y $INPUTS -filter_complex "$FC" -map "[mix]" -t "$T" -c:a pcm_s16le _raw.wav

# 최고점 측정
MAXV=$(ffmpeg -hide_banner -i _raw.wav -af volumedetect -f null - 2>&1 \
       | sed -n 's/.*max_volume: \(-*[0-9.]*\) dB.*/\1/p')

# 2패스 — 목표 최고점(-1.5dB)에 맞춰 보정
G=$(awk "BEGIN{printf \"%.2f\", -1.5-($MAXV)}")
ffmpeg -y -i _raw.wav -af "volume=${G}dB" -c:a pcm_s16le narration.wav
```

`-1.5dB`를 목표로 둔 건 인코딩 과정에서 살짝 넘칠 여지를 남기기 위해서다. 0dB에 딱 붙이면 AAC로 인코딩할 때 클리핑이 날 수 있다.

### 결과

```
 0~ 8초   평균 -18.1 dB   최대 -1.8 dB
 8~16초   평균 -17.1 dB   최대 -1.7 dB
16~24초   평균 -17.3 dB   최대 -1.5 dB
24~32초   평균 -17.3 dB   최대 -2.0 dB
32~40초   평균 -16.6 dB   최대 -1.8 dB
40~48초   평균 -17.5 dB   최대 -2.2 dB
```

**앞뒤 차이가 1.5dB 안으로 들어왔다.** 22dB에서 1.5dB로.

## 테스트 음원으로 원리 확인하기

실제 나레이션으로는 "입력 수로 나눈다"를 정확히 확인하기 어렵다. 문장마다 원래 크기가 조금씩 다르기 때문이다. 그래서 크기가 똑같은 테스트 음원으로 다시 재현했다.

최고점 -6dBFS(진폭 0.5)짜리 440Hz 사인파 2초를 6개 만들고, 1초·4초·7초…에 하나씩 배치해 합쳤다. 문장 6개가 겹치지 않고 차례로 나오는 상황과 같다.

```bash
N=6; IN=""; FC=""; L=""
for i in $(seq 0 $((N-1))); do
  IN="$IN -f lavfi -i aevalsrc=0.5*sin(2*PI*440*t):s=48000:d=2"
  D=$((1000 + i*3000))
  FC="$FC[$i:a]adelay=$D|$D[a$i];"; L="$L[a$i]"
done
ffmpeg -y $IN -filter_complex "${FC}${L}amix=inputs=$N:dropout_transition=0[m]" \
  -map "[m]" -c:a pcm_s16le default.wav
```

같은 명령에 `:normalize=0`만 붙여 한 번 더 뽑고, 각 톤 구간의 최고점을 쟀다(ffmpeg 8.1.1).

| 톤 | 그 시점에 살아 있는 입력 | 기본값(normalize=1) | 이론값 −20·log₁₀(n) | normalize=0 |
|---|---|---|---|---|
| 1번 | 6개 | −21.6 dB | −6 −15.6 | −6.0 dB |
| 2번 | 5개 | −20.0 dB | −6 −14.0 | −6.0 dB |
| 3번 | 4개 | −18.1 dB | −6 −12.0 | −6.0 dB |
| 4번 | 3개 | −15.6 dB | −6 −9.5 | −6.0 dB |
| 5번 | 2개 | −12.0 dB | −6 −6.0 | −6.0 dB |
| 6번 | 1개 | −6.0 dB | −6 −0 | −6.0 dB |

기본값 열은 이론값과 0.1dB 안에서 맞는다. **살아 있는 입력이 n개면 소리가 1/n이 된다**는 설명이 그대로 확인된다. 아직 소리가 나오기 전인 입력도, 앞에 무음이 붙어 있을 뿐 살아 있는 입력으로 센다. 그래서 첫 문장이 가장 작다.

## 아예 섞지 않는 방법: concat

문장들이 절대 겹치지 않는다면 굳이 **섞을(mix)** 필요가 없다. 무음과 문장을 순서대로 **이어 붙이면(concat)** 된다. 나누기가 일어날 여지가 처음부터 없다.

```bash
# 무음 1초 → 톤 2초를 6번 반복해 이어 붙이기
G="anullsrc=r=48000:cl=mono:d=1"
T="aevalsrc=0.5*sin(2*PI*440*t):s=48000:d=2"
IN=""; L=""; k=0
for i in 0 1 2 3 4 5; do
  IN="$IN -f lavfi -i $G -f lavfi -i $T"; L="$L[$k:a][$((k+1)):a]"; k=$((k+2))
done
ffmpeg -y $IN -filter_complex "${L}concat=n=12:v=0:a=1[m]" -map "[m]" -c:a pcm_s16le concat.wav
```

결과는 6개 톤 모두 −6.0dB, 전체 길이는 정확히 18.000초였다. 둘 중 무엇을 쓸지는 이렇게 고른다.

| | `adelay` + `amix normalize=0` | 무음 + `concat` |
|---|---|---|
| 시각 지정 | 절대 시각("3.8초에 시작")을 그대로 넣는다 | 앞 문장 끝과 다음 문장 시작 사이의 **무음 길이를 계산**해야 한다 |
| 겹침 허용 | 된다(대신 클리핑 관리 필요) | 안 된다. 겹치게 하려면 결국 mix가 필요하다 |
| 실수했을 때 | `normalize`를 빼먹으면 이 글의 버그가 다시 난다 | 무음 계산이 틀리면 뒤 문장이 전부 밀린다 |

나는 컷시트에 "몇 초에 무슨 문장"이 절대 시각으로 적혀 있어서 `adelay` + `normalize=0`을 그대로 썼다. 문장 길이만 알고 시작 시각이 없는 파이프라인이라면 concat이 더 단순하다.

## 겹치는 소리와 2패스의 함정

앞에서 "겹치지 않으니 클리핑 걱정이 없다"고 했다. 그럼 겹치면 실제로 얼마나 넘칠까? 같은 -6dBFS 톤 3개를 0초·0.5초·1초에 시작시켜 1~2초 구간에서 셋이 동시에 울리게 했다.

| 조건 | 최고점 | 최고점에 붙은 샘플 수 |
|---|---|---|
| `normalize=0`, 32비트 float로 저장 | **+3.5 dBFS** (0 넘음) | — |
| `normalize=0`, 16비트로 저장 | 0.0 dBFS | **25,920개** (파형 윗부분이 잘림) |
| 각 입력에 `volume=-9.54dB`(1/3) 후 `normalize=0` | −6.0 dBFS | 80개 (정상) |

진폭 0.5짜리 셋이 같은 위상으로 겹치면 1.5가 된다. 16비트 정수에는 1.0을 넘는 값을 담을 수 없으니 그 위는 잘려 나간다. 이게 클리핑이다.

여기서 **본문의 2패스 스크립트에 함정**이 있다. 1패스를 `pcm_s16le`로 뽑으면 이미 잘린 뒤라, 2패스에서 음량을 줄여도 잘린 파형은 복구되지 않는다. 측정 도구도 속는다. +3.5dBFS로 넘친 float 파일을 `volumedetect`로 재면 `max_volume: 0.0 dB`가 나온다. 실제보다 3.5dB 낮게 보고하는 셈이다. 같은 파일을 `astats`로 재면 `Peak level dB: 3.52`로 제대로 나온다.

그래서 겹침이 있는 믹스라면 2패스를 이렇게 바꾼다.

```bash
# 1패스 — 32비트 float로 저장해 0dB 위의 값도 보존
ffmpeg -y $INPUTS -filter_complex "$FC" -map "[mix]" -c:a pcm_f32le _raw.wav

# 최고점 측정 — volumedetect 대신 astats
MAXV=$(ffmpeg -hide_banner -i _raw.wav \
  -af astats=measure_overall=Peak_level:measure_perchannel=none -f null - 2>&1 \
  | sed -n 's/.*Peak level dB: \(.*\)/\1/p')

# 2패스 — 이 단계에서 16비트로
G=$(awk "BEGIN{printf \"%.2f\", -1.5-($MAXV)}")
ffmpeg -y -i _raw.wav -af "volume=${G}dB" -c:a pcm_s16le narration.wav
```

위 겹침 예제에 적용하면 보정값이 −5.02dB로 계산되고, 최종 최고점은 −1.50dBFS, 잘린 샘플은 없었다. 내 원래 파이프라인은 문장이 겹치지 않아 16비트 1패스로도 문제가 없었다. 그래도 나중에 배경음이 깔리면 바로 걸리는 함정이라 스크립트는 float 방식으로 바꿔 두는 편이 안전하다.

## 최고점 맞추기 vs 체감 음량(LUFS) 맞추기

2패스는 **최고점**을 맞추는 방법이다. 그런데 최고점이 같다고 귀에 들리는 크기가 같은 건 아니다. 사인파와 핑크 노이즈를 둘 다 최고점 −1.5dBFS로 맞추고, 사람 귀의 감도를 반영한 체감 음량(EBU R128의 통합 라우드니스, 단위 LUFS)을 `ebur128` 필터로 쟀다.

| 소리 | 최고점 맞춘 뒤 최고점 | 최고점 맞춘 뒤 체감 음량 | `loudnorm=I=-16` 후 체감 음량 | `loudnorm` 후 최고점 |
|---|---|---|---|---|
| 사인파 | −1.5 dBFS | −5.2 LUFS | −16.0 LUFS | −12.3 dBFS |
| 핑크 노이즈 | −1.4 dBFS | −13.9 LUFS | −16.0 LUFS | −3.5 dBFS |

최고점은 같은데 체감 음량은 **8.7LU** 차이 난다. 반대로 `loudnorm`으로 체감 음량을 맞추면 최고점이 9dB 가까이 벌어진다. 무엇을 기준으로 맞출지 정해야 한다.

- **같은 엔진, 같은 설정으로 만든 소리끼리**(이번 TTS 문장들): 성격이 비슷해 최고점 기준으로도 충분했다. 실제로 구간 평균이 1.5dB 안에 들어왔다.
- **성격이 다른 소리를 섞거나 플랫폼에 맞춰 내보낼 때**(나레이션 + 배경음악, 여러 사람 목소리): 체감 음량 기준인 `loudnorm`이 맞다.

`loudnorm`을 쓸 때 하나 주의할 점이 있다. 내 환경에서는 출력 샘플레이트가 **192kHz**로 바뀌어 나왔다. 뒤에 `-ar 48000`을 붙여 원래 샘플레이트로 돌려놓아야 한다.

```bash
ffmpeg -i narration.wav -af loudnorm=I=-16:TP=-1.5:LRA=11 -ar 48000 out.wav
```

## 왜 못 알아챘나

이 버그가 오래 살아남은 이유가 있다.

**작업 중에는 파형이나 마지막 부분만 확인하게 된다.** 마지막 문장은 살아 있는 입력이 1개라 원래 크기로 나오니, 끝부분만 들으면 "잘 나왔네" 싶다. 앞부분이 조용한 건 "원래 이 문장이 작게 녹음됐나" 하고 넘어가기 쉽다.

**구간별로 재보기 전까지는 안 보인다.** 그래서 오디오를 합치는 파이프라인에는 **구간 음량 측정을 검수 절차에 못 박아두는 게 낫다.** 위의 `for` 루프 한 줄이면 된다.

> **🧭 기획자·사업자라면**
> **"들어보니 괜찮다"는 검수가 아니다.** 사람 귀는 절대 크기에 둔감하고, 특히 앞뒤를 이어 들으면 서서히 커지는 변화를 잘 못 잡는다. 이런 항목은 **판정 기준을 숫자로 정해두고**(예: 구간 평균 편차 3dB 이내) 자동으로 재게 해야 한다.
> 그리고 **라이브러리 기본값은 누군가의 다른 상황에 맞춰진 값**이다. `amix`의 `normalize=1`은 "여러 소리를 동시에 섞는" 전형적 용도에는 맞는 기본값이고, 내 용도(시간상 겹치지 않는 문장들)에는 정반대로 작동했다. 기본값을 쓰기로 했다면 **그 기본값이 가정하는 상황이 내 상황과 같은지** 한 번은 확인해야 한다.
{: .prompt-tip }

## 사용한 기술

- **`amix=…:normalize=0`** — 살아 있는 입력 수로 나누는 동작을 끈다
- **`adelay`** — 각 오디오를 원하는 시각에 배치
- **`volumedetect`** — 평균·최고 음량 측정. 구간을 잘라 반복 측정하면 시간에 따른 변화가 보인다
- **2패스 게인 보정** — 재고 → 차이만큼 `volume=NdB`. 겹침이 있으면 1패스는 `pcm_f32le`, 측정은 `astats`
- **`concat` + `anullsrc`** — 겹치지 않는 소리를 섞지 않고 무음과 함께 이어 붙이기
- **`ebur128` / `loudnorm`** — 체감 음량(LUFS) 측정과 맞추기

## 정리

- **`amix`의 `normalize`는 기본이 켜짐이고, 살아 있는 입력 수로 나눈다.** 입력들이 시간차로 끝나면 뒤로 갈수록 커진다.
- `dropout_transition`은 이 문제와 무관하다. **꺼야 하는 건 `normalize`다.** 소리가 겹치지 않으면 `concat`으로 이어 붙이는 방법도 있다.
- 겹치는 믹스를 2패스로 맞출 때는 1패스를 float로 뽑고 `astats`로 잰다. 16비트와 `volumedetect`는 0dB 위를 못 본다.
- **구간별 음량 측정을 검수에 넣어라.** 끝부분만 들으면 절대 안 잡힌다.
