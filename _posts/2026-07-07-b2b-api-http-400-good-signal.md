## 문제

한 글로벌 물류기업의 배송 추적 API를 연동하려고, 개발자 포털에서
OAuth 애플리케이션을 만들고 Client Credentials 방식으로 액세스 토큰을 발급받았다.
발급까지는 순조로웠다. 그리고 첫 API 호출을 던졌다.

```bash
curl -H "Authorization: Bearer <access_token>" \
  "https://gateway.api.example.com/track-trace/shipment/v2/shipments"
```

돌아온 건 이거였다.

```json
{"timestamp":"...","status":400,"error":"Bad Request","path":"/tracking-overviews/external/api/svc/track-trace/shipments"}
```

**HTTP 400 Bad Request.** 순간 "토큰이 잘못됐나? 인증이 안 먹었나?" 싶었다.
그런데 여기서 400을 인증 실패로 오해하고 토큰 발급부터 다시 파면, 멀쩡한 걸
붙잡고 시간을 버리게 된다.

## 원인

400은 인증 실패가 아니다. **인증을 통과했다는 증거**다. 상태코드가 어디서
막혔는지를 알려준다고 보면 된다.

- **401**이면 토큰 문제 — API 게이트웨이 문턱조차 못 넘은 것.
- **403**이면 인증은 됐지만 구독·권한 문제.
- **400**이면 인증·권한 다 통과하고 **백엔드 서비스까지 요청이 도달**한 뒤,
  요청 형식(필수 파라미터 등)이 틀렸다는 것.

결정적 단서는 400 응답 본문의 `path`였다. 내가 호출한 건
`/track-trace/shipment/v2/shipments`인데, 에러에 찍힌 경로는
`/tracking-overviews/external/api/svc/...`로 **내부 서비스 주소로 치환돼**
있었다. 게이트웨이가 요청을 내부로 라우팅했다는 뜻 — 즉 인증·구독·라우팅이
전부 정상 작동했다는 증거다.

그럼 왜 400인가? 스펙을 확인하니 `GET /shipments`는 `reference`(고객 참조번호)
쿼리 파라미터가 **필수**였다. 파라미터 없이 불러서 400이 난 것이다.

## 해결 과정

### 1. 토큰 발급 (Client Credentials)

```bash
curl -X POST "https://portal.api.example.com/oauth2/token" \
  -u "<ConsumerKey>:<ConsumerSecret>" \
  -d "grant_type=client_credentials"
```

응답의 `access_token`이 Bearer 토큰. 여기서 **콘솔의 Key Configuration 화면은
그냥 Generate Keys만 누르면 된다** — Client Credentials 방식은 Callback URL도,
별도 입력도 필요 없다. 이 단계가 됐다면 인증 자체는 성공이다.

### 2. 필수 파라미터 없는 엔드포인트로 연결 검증

`GET /shipments`는 `reference`가 필수라 검증용으로는 번거롭다. 그래서 필수
필드가 없는 **검색 엔드포인트**로 연결만 확인했다.

```bash
curl -X POST "https://gateway.api.example.com/track-trace/shipment/v2/shipments-search" \
  -H "Authorization: Bearer <access_token>" \
  -H "Content-Type: application/json" \
  -d '{"pagination":{"pageNumber":1,"pageSize":10},"filters":{}}'
```

결과:

```json
{"shipments":[],"page":{"totalElements":0,"totalPages":0,"currentPage":0,"size":20,"hasNext":false,"hasPrevious":false}}
```

**HTTP 200 + 빈 배열.** 이게 연동 검증의 결승선이다. 우리 계정에 아직 운송
건이 없으니 **빈 배열이 정답**이고, 이 응답을 받은 순간 인증·구독·게이트웨이
라우팅·요청 형식이 전 구간 검증된 것이다.

### 3. 함정: 익명 스펙의 서버 URL

한 가지 더 삽질 포인트. 로그인 없이 받은 OpenAPI 스펙의 `servers`에는
`https://internal.api.example.com/...` 내부 주소가 적혀 있었다. 실제
호출 주소는 로그인 후 포털에서 받은 스펙의 `https://gateway.api.example.com/...`
였다. 내부 주소로 쏘면 당연히 안 닿는다. (이 익명 스펙 이야기는
[회원가입 없이 스펙 받아내기](/posts/wso2-devportal-api-no-login/)에 정리했다.)

## 첫 호출에서 만날 수 있는 응답 전부 — 진단표

이번에 실제로 본 건 400과 200이다. 하지만 연동 첫날에는 다른 코드도 얼마든지 나온다. 상태코드마다 **요청이 어디까지 갔는지**와 **먼저 볼 곳**을 표로 정리했다. 의미는 HTTP 표준(RFC 9110)과 OAuth 표준(RFC 6749·6750), 429는 RFC 6585를 기준으로 했다.

| 코드 | 요청이 어디까지 갔나 | 먼저 확인할 것 | 표준이 정한 단서 |
|---|---|---|---|
| **401** | 게이트웨이 문턱에서 막힘 | 토큰 만료, `Bearer ` 접두어 누락, 다른 환경(테스트↔운영)의 토큰 | 401 응답에는 `WWW-Authenticate` 헤더가 **반드시** 있어야 한다(RFC 9110 §15.5.2) |
| **403** | 인증은 통과, 권한에서 막힘 | API 구독 신청 여부, 토큰의 scope | 같은 자격 증명으로 **자동 재시도하지 말라**(SHOULD NOT, §15.5.4) |
| **404** | 경로를 못 찾음 | base URL, 버전(`v1`/`v2`), 익명 스펙의 내부 주소 | — |
| **405** | 경로는 맞는데 메서드가 틀림 | GET으로 불렀는데 POST 전용인지 | 405 응답에는 허용 메서드를 담은 `Allow` 헤더가 **반드시** 있다(§15.5.6) |
| **415** | 본문 형식을 못 받음 | `Content-Type: application/json` 누락 | 이 메서드가 지원하지 않는 형식의 본문(§15.5.16) |
| **400** | 백엔드까지 도달, 요청 내용이 틀림 | 필수 파라미터, 본문 필드 이름·타입 | 잘못된 문법·형식 등 클라이언트 오류로 판단(§15.5.1) |
| **429** | 호출 한도 초과 | 반복문·재시도 루프가 폭주하는지 | `Retry-After` 헤더로 기다릴 시간을 줄 수 **있다**(RFC 6585 §4) |
| **502·504** | 게이트웨이 뒤 서버가 이상 | 내 요청 문제가 아닐 가능성이 크다 | 게이트웨이가 상위 서버에서 잘못된 응답(502)·제때 응답 없음(504)을 받음(§15.6.3·15.6.5) |
| **503** | 서버가 일시적으로 못 받음 | 점검 공지, 과부하 | `Retry-After`를 줄 수 있다(§15.6.4) |

이번 글의 `shipments-search`처럼 POST 전용 엔드포인트를 GET으로 부르면 405가 나와야 하고, JSON 본문을 보내면서 `Content-Type`을 빼먹으면 415나 400이 나온다. 표에서 위로 갈수록 "아직 문 앞", 아래 400부터는 "안까지 들어갔다"로 읽으면 된다.

> 표준은 서버가 이렇게 **해야 한다**는 약속이지, 모든 API가 지키는 건 아니다. 어떤 서버는 권한 문제에도 404를 돌려준다. 리소스가 있다는 사실 자체를 숨기려는 것인데, 표준도 이를 허용한다(RFC 9110 §15.5.4). 표는 출발점으로 쓰고, 최종 판단은 응답 본문과 헤더로 한다.
{: .prompt-warning }

## 상태코드 다음에 볼 곳 — 응답 헤더와 본문

### 헤더: 서버가 이유를 적어 두는 곳

상태코드만 보고 추측하기 전에 `curl -i`(헤더 포함 출력)로 헤더부터 본다.

- **401이면 `WWW-Authenticate`**. Bearer 토큰 API는 여기에 이유를 적는다. 토큰이 만료됐거나 위조됐으면 `error="invalid_token"`, 권한(scope)이 모자라면 `error="insufficient_scope"`다. 표준은 앞의 경우 401, 뒤의 경우 403을 돌려주도록 권장한다(RFC 6750 §3.1, SHOULD).
- **405면 `Allow`** — 이 경로에 쓸 수 있는 메서드 목록.
- **429·503이면 `Retry-After`** — 얼마나 기다렸다 다시 보낼지.

### 본문: 형식부터 확인

에러 본문 형식은 서버마다 다르다. 표준 형식으로는 **Problem Details**(RFC 9457, 이전 RFC 7807을 대체)가 있다. 응답의 `Content-Type`이 `application/problem+json`이면 다음 필드를 읽으면 된다.

| 필드 | 뜻 |
|---|---|
| `type` | 오류 종류를 가리키는 URI |
| `title` | 오류 종류의 짧은 설명 |
| `status` | 상태코드 |
| `detail` | 이번 요청에서 무엇이 틀렸는지 |
| `instance` | 이 오류가 난 특정 요청을 가리키는 값 |

이번에 받은 400 본문은 `timestamp`·`status`·`error`·`path`를 담은 **서버 고유 형식**이었다. 표준 형식이 아니어도 읽을 곳은 비슷하다. 무엇이 틀렸는지(`error`, `message`, `detail`)와 요청이 어디로 갔는지(`path`)를 본다. 이번 글의 결정적 단서였던 `path` 치환도 여기서 나왔다.

## 토큰 만료와 재발급 — Client Credentials의 규칙

연결 검증이 끝나면 다음 문제는 "토큰이 만료되면 어떻게 하나"다. Client Credentials 방식에는 사용자 로그인 방식과 다른 점이 있다.

**리프레시 토큰이 없다.** 표준은 이 방식의 토큰 응답에 리프레시 토큰을 **넣지 말라**고 한다(RFC 6749 §4.4.3, SHOULD NOT). 사용자가 개입하지 않으니 갱신용 토큰을 따로 둘 이유가 없다. 만료되면 처음과 똑같이 키와 시크릿으로 **다시 발급**받으면 된다.

**만료 시간은 `expires_in`(초 단위)에 온다.** 다만 이 필드는 필수가 아니라 권장(RECOMMENDED)이다(§5.1). 그래서 처리 방식을 두 겹으로 둔다.

1. `expires_in`이 오면 → 토큰을 저장해 두고, 만료 조금 전에 미리 재발급한다. 요청마다 새 토큰을 받으면 토큰 발급 API의 호출 한도에 걸릴 수 있다.
2. `expires_in`이 없거나 시계가 어긋났으면 → 401에 `error="invalid_token"`이 오면 재발급 후 **딱 한 번만** 다시 보낸다.

상태코드별 재시도 규칙은 이렇게 정리된다.

| 응답 | 할 일 |
|---|---|
| 401 `invalid_token` | 토큰 재발급 → 1회 재시도. 또 401이면 키·시크릿 자체를 의심 |
| 403 | 재시도하지 않는다. 구독·권한은 사람이 포털에서 풀어야 한다 |
| 429·503 | `Retry-After`만큼 기다린 뒤 재시도. 헤더가 없으면 간격을 점점 늘린다 |
| 400·404·405·415 | 재시도해도 같은 결과다. 요청을 고친다 |

**`curl -u`의 정체**: 토큰 발급 때 쓴 `-u "<ConsumerKey>:<ConsumerSecret>"`는 HTTP Basic 인증이다. 표준은 시크릿을 받은 클라이언트에 대해 인증 서버가 이 방식을 **반드시 지원**하도록 정해 두었다(RFC 6749 §2.3.1). 한 가지 함정이 있다. 표준상 키와 시크릿은 각각 **URL 인코딩한 뒤** Basic으로 묶는다. `curl -u`는 이 인코딩을 하지 않고 값을 그대로 보낸다. 그래서 시크릿에 `:`·`+`·`%` 같은 특수문자가 있으면 도구나 라이브러리에 따라 결과가 갈릴 수 있다. 한 도구에서는 되는데 다른 도구에서만 401이 난다면 이 부분을 본다.

## 연동 검증 체크리스트

이번 과정을 다음 연동에도 그대로 쓸 수 있게 순서로 정리했다.

1. **스펙 출처 확인** — 로그인 후 포털에서 받은 스펙의 `servers` 주소를 쓴다. 익명 스펙의 주소는 내부용일 수 있다.
2. **토큰 발급** — `200`과 `access_token`을 확인하고, `expires_in`이 오는지 본다.
3. **필수 파라미터 없는 엔드포인트로 호출** — `200`이면 인증·구독·라우팅이 모두 정상이다. 빈 배열도 성공이다.
4. **일부러 실패시켜 보기** — 토큰을 한 글자 바꿔 401이 오는지, 그때 `WWW-Authenticate`에 뭐가 오는지 본다. 에러 처리 코드는 실제 에러를 한 번은 받아 봐야 믿을 수 있다.
5. **필수 파라미터가 있는 엔드포인트** — 스펙대로 값을 넣어 `200`을 받는다. 테스트 데이터가 없으면 빈 결과가 정답일 수 있다.
6. **실데이터 확인** — 파트너 쪽에 실제 데이터가 쌓인 뒤의 일이다. 일정표에서 3~5와 칸을 나눈다.

## 사용한 기술

- **OAuth 2.0 Client Credentials** — 서버 간(machine-to-machine) 인증. 사용자
  로그인 없이 Consumer Key/Secret으로 액세스 토큰 발급. 리프레시 토큰 없이 만료 시 재발급(RFC 6749)
- **HTTP 상태코드** — 401(인증)·403(권한)·400(요청 형식)·200(성공)으로 실패
  지점 진단(RFC 9110)
- **Bearer 토큰 에러 코드** — `WWW-Authenticate`의 `invalid_token`·`insufficient_scope`(RFC 6750)
- **Problem Details** — 표준 에러 본문 형식 `application/problem+json`(RFC 9457)
- **curl** — 토큰 발급·API 호출 검증

> **🧭 기획자·사업자라면**
> 1. 외부 API 연동에서 "인증까지 됐나 / 데이터 권한까지 열렸나 / 실호출이 되나"는 **다른 단계**다. 200 빈 배열이라도 "연결은 검증됐다"는 마일스톤으로 잡으면, 실데이터가 없는 초기에도 연동 완료 여부를 명확히 보고할 수 있다.
> 2. 파트너와 API 연동 일정을 잡을 때 "토큰 발급"과 "실데이터 조회"를 같은 칸에 두지 말 것 — 토큰은 며칠, 실데이터는 계약·운송 데이터가 실제로 쌓여야 나온다. 이 둘을 분리하지 않으면 "API 연동 완료"의 정의가 흐려진다.
{: .prompt-tip }

## 정리

1. 외부 API 첫 호출의 400은 인증 실패가 아니라 **인증 통과 + 백엔드 도달** 신호다. 401(토큰)·403(권한)과 구분하자.
2. 400 응답 본문의 `path`가 내부 주소로 바뀌어 있으면 게이트웨이 라우팅이 정상 작동한 것 — 필수 파라미터를 확인하면 된다.
3. 연결 검증은 필수 파라미터 없는 엔드포인트로 `200 + 빈 배열`을 받으면 끝. 빈 배열은 실패가 아니다.
